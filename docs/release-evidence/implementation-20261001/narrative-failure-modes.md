# Canonical narrative runtime failure modes

Written before the new HTTP checks and runtime implementation. Confirmed owner
decisions require stories for every tied defined single-game extreme, and both
largest unanswered Boston runs in the Boston loss. Undefined measures keep
their approved clarification inputs. No question IDs or evaluation labels may
control the application response.

Failures to prevent:

- Closest/biggest-win/best-defense selection chooses one tied game, ranks a
  non-final game, uses an unrequested season or opponent, or silently defaults
  an undefined measure. Every selected canonical game must be represented.
- The normal three-claim fallback, model text limit, citation limit or evidence
  token bound drops tied games or one maximum run. A complete deterministic
  narrative remains available if complete reviewed wording cannot fit.
- Game stories invent plays or tactics from quarter/final totals. Show the
  verified final and period scores, without unsupported mechanisms or causes.
- Boston runs end at a quarter boundary or a zero-point event, or continue
  across any Knicks point, including a free throw. Use canonical sequence and
  retain every maximum with each scoring event ID, period, clock and scores.
- Duplicate event sequences, backwards scores, simultaneous team increments,
  missing score coverage, or a final-score mismatch certify an invalid run.
  Fail visibly without reporting an invented maximum.
- A newer release's event/period rows leak into the active release, or an
  unverified assistant narrative becomes the narrative's selected game/facts.
- Existing measure clarifications lose scope, comparison or boundary inputs.
  The five owner-approved ambiguous measures must remain clarifications.
- Missing games or measures dispatch paid inference during clarification, or
  replay/conflict behavior and monthly budget preservation regress.
- A model uses only part of a required narrative claim or omits a selected
  game/run in prose. Require complete coverage before accepting reviewed wording.

HTTP verification loads the original approved bundle through the real loader,
uses the actual ASGI route and disposable local Redis, prohibits provider
construction in disabled mode, and retains requests/responses/captures/replays
and budget receipts before assertions. Additional synthetic boundary and score
correction fixtures run through the same HTTP route. These are local behavior
checks, not frozen evaluation gold or paid provider-quality evidence.
